# Chroma Mempool ポリシー 草案 v0.1-draft

> これは草案である。実装は存在しない。
> ここに書かれているのは**ポリシー**であって、合意規則ではない。
> メンプールはブロックの妥当性に関与せず、
> ノードごとに内容が違ってよい（SPEC §2 の対象外）。

## 1. 前提：手数料が無いということ

Chroma に手数料は無い。ブロック報酬は 1 CHR 固定で、
トランザクションは1 unit も支払わない。
したがってメンプールに**入場料が存在しない**。

この事実から出発すると、目標を正しく置き直す必要がある。

**手数料の無いチェーンは、spam を価格で締め出すことができない。**
できるのは、spam が占める**割合を抑えること**だけである。
「spam を防ぐ」ではなく「**spam に全部は取られない**」を目標とする。
この区別を曖昧にした設計は、必ずどこかで嘘をつく。

手数料のあるチェーンでは、混雑すると価格が上がり、
払えない要求が自然に落ちる。Chroma にはその機構が無い。
代わりに次の4つで支える。

| 手段            | 何を保証するか                  |
| ------------- | ------------------------ |
| 状態に裏打ちされた入場   | 残高の無い者は1件も入れられない         |
| ピアごとの流量制限     | 1接続が注ぎ込める速度に上限がある        |
| 送信者ごとの上限      | 口座1つが占められる枠に上限がある        |
| 残高で重み付けた公平性   | 口座を分割しても取り分が増えない         |

## 2. 現状

[`crates/chroma-p2p`](../crates/chroma-p2p/) に既にあるもの、無いものを先に挙げる。
設計は既存の上に足すものであって、置き換えるものではない。

### 既にあるもの

| 防御          | 実装                                        | 値                   |
| ----------- | ----------------------------------------- | ------------------- |
| ピアごとの tx 流量 | `Peer::allow_transaction`                 | `TX_RATE_LIMIT` = 10/秒 |
| 不正署名の罰      | `score_bad(10)` → `PEER_BAN_THRESHOLD` 100 | 10件で ban            |
| 接続数         | `MAX_INBOUND_PEERS` 16 + `MAX_OUTBOUND_PEERS` 8 | 24              |
| 重複の排除       | `Mempool::add_transaction`                | tx ハッシュ             |
| 全体の容量       | `MAX_MEMPOOL_TXS` / `MAX_MEMPOOL_SIZE`    | 100,000 件 / 50 MB   |

**流量制限は既に効いている。** 24ピア × 10/秒 = 最大 240 tx/秒。
署名検証を1件 50µs とすると CPU の 1.2% にすぎず、
ブロックの容量（`MAX_BLOCK_SIZE / Transaction::SERIALIZED_SIZE` ≒ 7,900件、
10秒あたり ≒ 790 tx/秒）より低い。
**ネットワーク越しに検証コストで潰すことはできない。**
不正署名は10件で ban されるため、その経路も塞がっている。

### 無いもの

* **nonce と残高の検査**。`add_transaction` は重複と容量しか見ない
* 送信者あたりの上限
* 期限切れ（`MempoolEntry::added_at` は 0 で固定されている）
* 満杯時の追い出し（エラーを返して終わり）
* ブロック組み立て時の選択規則（今は入った順）
* `fee_per_byte` という使われないフィールドが残っている

**最大の穴は1つ目である。** 鍵ペアを作るだけで、
残高を1 unit も持たない口座から有効な tx を作れ、
それが受理され、さらに**中継までされる**。
コストは鍵生成と 132 バイトの送信だけで、
攻撃者はチェーン上に何も持つ必要がない。

## 3. 入場規則

### 3.1 実効状態

判定は確定状態ではなく実効状態に対して行う。

```text
effective_nonce(S)   = state.nonce(S) + (メンプール内の S 発 tx の件数)
effective_balance(S) = state.balance(S) − Σ(メンプール内の S 発 tx の amount)
```

確定状態だけで見ると、同じ送信者の2件目が常に弾かれるか、
合計残高を超える組を受け入れてしまう。どちらも正しくない。

### 3.2 検査の順序

**安い検査から順に行う。この順序はポリシーの一部である。**

| #  | 検査                             | 費用       | 失敗時                   |
| -- | ------------------------------ | -------- | --------------------- |
| 1  | 長さ（`Transaction::SERIALIZED_SIZE`） | 定数    | 破棄                    |
| 2  | 復号                             | 定数       | 破棄 + `score_bad`      |
| 3  | メンプールに同一ハッシュ                   | ハッシュ表1回  | 破棄（エラーではない）           |
| 4  | 送信者の口座が存在し、残高 > 0             | 状態1回     | 破棄 + `score_bad`      |
| 5  | `nonce == effective_nonce`     | 状態1回     | 破棄                    |
| 6  | `amount ≤ effective_balance`   | 状態1回     | 破棄                    |
| 7  | 送信者あたりの未確定件数 < 上限              | 表1回      | 破棄                    |
| 8  | **署名の検証（BIP-340 Schnorr）**     | **≒50µs** | 破棄 + `score_bad(10)` |
| 9  | メンプール全体の容量                     | 定数       | 追い出し（§5）              |

**署名検証を最後に置くのが要点である。**
状態の参照はハッシュ表1回、署名検証はその1000倍近く高い。
残高を持たない口座からの tx は、**署名を検証する前に落ちる**。

現在の実装は逆になっている
（[`lib.rs`](../crates/chroma-p2p/src/lib.rs) の `MessageType::Tx` は
署名検証をしてから `add_transaction` を呼ぶ）。
順序を入れ替えるだけで、残高の無い口座からの spam は
署名検証を1回も踏ませずに落ちるようになる。

順序を入れ替えても安全性は変わらない。4〜7 が読むのは
tx が自称する送信者の**公開情報**（`chroma_getAccount` で誰でも引ける）だけであり、
署名を先に見なくても漏れるものが無い。
署名の通らない tx が受理されないことは 8 が保証する。

### 3.3 送信者あたりの上限

`MAX_PENDING_PER_SENDER` を導入する。**現在どの定数にも存在しない。**
値は 8 を提案するが、決めるのは運用の判断である。

上限があると、口座1つが占められる枠が有限になる。
上限が無いと、残高の大きい口座1つでメンプール全体を埋められる。

### 3.4 最小送金額

`MIN_RELAY_AMOUNT` を導入する。**合意規則ではなく中継ポリシーとする。**
これを下回る tx はブロックに入れても妥当だが、メンプールは受け取らず中継もしない。

1 CHR = 1,000,000 units なので、最小額が無ければ
ブロック報酬1個で 100万個の口座に配れる。
最小額を 1,000 units（0.001 CHR）とすれば 1,000 個に落ちる。

**合意規則にしない理由。** 合意規則にするとハードフォークになり、
値を後から変えられない。中継ポリシーなら、各ノードが独立に調整でき、
古いブロックの妥当性にも影響しない。Bitcoin の dust limit と同じ立場である。

## 4. 攻撃と、どこまで防げるか

正直に書く。**以下は「防げる」と「割合を抑えられる」を区別している。**

### 4.1 残高を持たない spam — 防げる

鍵ペアだけで tx を作る攻撃。§3.2 の 4 で落ちる。
署名検証にも到達しない。**完全に防げる。**

現状はこれが素通りする。ここが最も大きな改善になる。

### 4.2 署名検証の CPU 攻撃 — 既に防げている

不正署名を大量に送る攻撃。
ピアごとに 10/秒、不正署名10件で ban。**既存の実装で塞がっている。**

§3.2 の順序変更で、さらに 4〜7 で落ちるものは検証に達しなくなる。

### 4.3 nonce に穴を空けた投機的な列 — 防げる

`nonce + 5` のような、まだ使えない tx を大量に送る攻撃。
§3.2 の 5 が `nonce == effective_nonce` を厳密に要求するので落ちる。
**キューを持たない**という選択が、そのまま防御になっている。

代償として、送信者は自分の tx が入る順序を守る必要がある。
これは手数料の無いチェーンでは妥当な制約である
（置き換えができない以上、投機的に並べる意味がない）。

### 4.4 残高を持つ攻撃者 — 防げない。割合を抑えるだけ

**ここが手数料の無いチェーンの本質的な限界である。**

攻撃者が 1 CHR を持ち、それを多数の口座に分けて、
各口座から自分宛に送り続ける。送金先が自分なので**残高は減らない**。
`MIN_RELAY_AMOUNT` を 1,000 units とすれば、1 CHR は 1,000 口座に分けられ、
`MAX_PENDING_PER_SENDER` が 8 なら 8,000 件を常時占有できる。

* 口座を作る（＝送金する）には、その送金自体が採掘される必要がある。
  つまり**設置コストはブロック容量で律速される**
* しかし一度設置すれば、残高は消費されないので**繰り返しは無料**である

**手数料が無い以上、これは価格で防げない。** 防げるふりをしてはいけない。
できるのは、この攻撃者が**ブロックの全部を取らないようにする**ことだけである。

### 4.5 中継の増幅 — 既に防げている

受理しなかった tx は中継しない（現在の実装もそうなっている）。
受理した tx だけを、受け取った相手を除くピアへ流す。
追い出した tx を後から中継してはならない。

## 5. 満杯のとき

`MAX_MEMPOOL_TXS` に達したら、エラーを返すのではなく**追い出す**。
今の実装は満杯でエラーを返すため、先に入った者が居座り、
後から来た正当な tx が入れない。

追い出す対象は、**`未確定件数 / 残高` が最も大きい送信者**の、
その送信者の中で最も nonce が大きいものとする。

* 分母が残高なので、**口座を分割しても得をしない**。
  1 CHR を 1,000 口座に分けても、合計の比は変わらない
* 分子が件数なので、多く積んでいる送信者から先に削られる
* 送信者の中では nonce の大きい側から削る。
  nonce の列に穴を空けないため（§3.2 の 5 が穴を許さない）

新しく入る tx がこの基準で最下位なら、追い出さずにその tx を拒否する。

## 6. 期限切れ

`MempoolEntry::added_at` に実際の時刻を入れ（現在は 0 固定）、
`MEMPOOL_EXPIRY_SECS` を超えた項目を落とす。1時間を提案する。

手数料が無いので「安すぎて永久に入らない」tx は存在しないが、
送信者の nonce が別の経路で進んだ tx は永久に入らない。
それを抱え続ける理由がない。

## 7. ブロックの組み立て

**メンプールがブロック容量を超えたとき、何を入れるかが最後の防衛線である。**
`MAX_MEMPOOL_TXS` は 100,000、ブロックは 7,900 件強なので、
混雑すれば必ず選択が発生する。

### 7.1 残高で重み付ける

送信者を**残高に比例した重み**で選び、選ばれた送信者からは
nonce の小さい順に取る。同じ重みなら古い順。

なぜ残高かというと、**分割しても総和が変わらない唯一の量**だからである。

| 選択規則      | 攻撃者が口座を1,000個に分けたとき |
| --------- | -------------------- |
| 送信者ごとに公平  | 取り分が **1,000倍** になる  |
| 古い順（FIFO） | 先に流し込んだ側が前を占める       |
| **残高で重み付け** | **取り分は変わらない**        |

送信者ごとの公平性は、口座が安く作れる以上、sybil に破られる。
残高による重み付けはそれを受けない。

### 7.2 これが意味すること

これは手数料による優先度の、手数料なしでの対応物である。
**残高の大きい者が先に入る。** 手数料のあるチェーンで
「多く払う者が先に入る」のと同じ性質であり、支払いが無いだけである。

公平とは言えない。しかし、
**分割で取り分を増やせない**という性質は、他の規則にはない。
そこを取るという選択である。

合意規則ではないので、採掘者は別の規則を選んでよい。
これは推奨であって、強制ではない。

## 8. 提案する定数

いずれも**現在は存在しない**。値は提案であり、決めるのは運用の判断である。

| 名前                       | 提案値            | 何を縛るか          |
| ------------------------ | -------------- | -------------- |
| `MAX_PENDING_PER_SENDER` | 8              | 口座1つが占める枠      |
| `MIN_RELAY_AMOUNT`       | 1,000 units    | 口座を増やす費用       |
| `MEMPOOL_EXPIRY_SECS`    | 3,600          | 入らない tx を抱える時間 |

既存の `TX_RATE_LIMIT`（10/秒）、`PEER_BAN_THRESHOLD`（100）、
`MAX_MEMPOOL_TXS`（100,000）は変更しない。

## 9. 未解決事項

### 9.1 Reorg で戻る tx

ブロックが巻き戻ると、そこに入っていた tx はメンプールに戻すべきである。
現在の実装はそれをしていない（採掘時に `remove_transactions` するだけ）。

戻す場合、実効状態（§3.1）を再計算する必要があり、
戻した結果 `MAX_PENDING_PER_SENDER` を超えることがありうる。
**戻す tx は上限の対象外とするか、超えた分を落とすか**を決めていない。
前者のほうが正しく見えるが、それを悪用する経路がないかは検討していない。

### 9.2 残高の重み付けと採掘者の利害

§7.1 は採掘者に、残高の大きい送信者を優先する動機を与えない
（手数料が無いので、誰を入れても報酬は同じ）。
つまりこの規則は**採掘者の善意に依存している**。
従わない採掘者を検出も罰もできない。

手数料のあるチェーンでは、採掘者の利害が優先度規則を自然に強制する。
Chroma にはそれが無い。これは設計の弱点であり、
「ポリシーは強制できない」という以上のことは今のところ言えない。

### 9.3 最小送金額と少額決済

`MIN_RELAY_AMOUNT` を 1,000 units（0.001 CHR）にすると、
それ未満の送金がネットワークを通らなくなる。
最小単位が 10⁻⁶ CHR であることの意味が、その分だけ薄れる。

spam の費用と少額決済の可否は同じつまみの両端にあり、
どちらを取るかは決めていない。
