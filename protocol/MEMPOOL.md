# Chroma 資源制限ポリシー 草案 v0.2-draft

> これは草案である。実装はまだ無い。
> ここに書かれているのは**ポリシー**であって、合意規則ではない。
> このポリシーの有無・内容がノード間で違っても、
> 全ノードは全ブロックについて同じ判断をする。
> 唯一の例外は §9（合意側の床）であり、そこだけは合意規則である。

## 1. 前提：手数料が無いということ

Chroma に手数料は無い。ブロック報酬は 1 CHR 固定で、
トランザクションは1 unit も支払わない。
したがってメンプールに**入場料が存在しない**。

手数料のあるチェーンでは、混雑すると価格が上がり、払えない要求が落ちる。
Chroma にはその機構が無いので、**別の希少資源で置き換える**必要がある。

## 2. 軸：口座ではなく資源

置き換える資源を何にするかで、設計の成否が決まる。

**口座を軸にしてはいけない。** 口座は `getrandom` で無限に作れる。
口座あたりの上限をいくら設けても、攻撃者は口座を増やすだけで回避する。
「1口座あたり N 件まで」という規則は、
攻撃者が口座を M 個持てば実質 N×M 件になる。

**接続を軸にする。** 攻撃者が100万アドレスを持っていても、
それを1つのノードに流し込むには接続が要る。
そして接続はタダではない。IP と帯域と、相手ノードの受け入れ枠を消費する。

> 攻撃者が1アドレスでも100万アドレスでも、
> 最終的に1ノードへ投入できる資源量を制限すればいい。

これが本設計の全体である。以降はその具体化にすぎない。

## 3. 三層

上限を1種類だけ置くと必ず抜け道が残る。**三層を重ねる。**

| 層          | 何を縛るか            | 抜けようとすると             |
| ---------- | ---------------- | -------------------- |
| **グローバル**  | ノード全体の総量         | 何をしても総量が超えない         |
| **接続単位**   | 1接続・1プレフィックスの取り分 | 接続を増やすしかない           |
| **ピア単位**   | 時間あたりの流量         | 待つしかない               |

* グローバルだけだと、1接続が全部取ってしまう
* 接続単位だけだと、接続を増やせば総量が伸びる
* ピア単位だけだと、時間をかければ総量が伸びる

三層あると、攻撃者は**同時に三つとも破らなければならない**。

本設計は既存の上に足すものであって、置き換えるものではない。

| —     | 期限切れ（`added_at` が 0 で固定）   |

## 5. グローバル上限

最外周の壁である。**攻撃者が何をしようと、ここは超えられない。**

現在の値をそのまま採用し、変更しない。

| 資源           | 上限        |
| ------------ | --------- |
| メンプール件数      | 100,000   |
| メンプール容量      | 50 MB     |
| ブロック         | 1 MiB     |
| トランザクション     | 132 バイト固定 |
| 接続           | 16 + 8    |

トランザクションが固定長であることが、ここでは効いている。
可変長なら「小さいものを大量に」と「大きいものを少数」で
別々の見積りが要るが、132バイト固定なら件数がそのままバイト数である。

**ブロックの件数に独立した上限は置かない。**
1 MiB ÷ 132 バイト = 7,943 件が自然な上限であり、これ以上の規則は要らない。

> `miner.rs` の `MAX_BLOCK_TXS = 10_000` と、
> `validate_block` の `MAX_TRANSACTION_SIZE`（64 KiB）検査は、
> どちらもサイズ上限より緩いため一度も発火しない。死んだ定数である。

## 6. 接続単位の割当

### 6.1 メンプール枠の課金

**本設計の中心はここにある。**

メンプールの各項目を、**それを持ち込んだ相手**の勘定に付ける。
1つの勘定が占有できる枠に上限を置く。

```text
MEMPOOL_QUOTA_PER_SOURCE = MAX_MEMPOOL_TXS / (MAX_INBOUND_PEERS + MAX_OUTBOUND_PEERS)
                         = 100,000 / 24 ≒ 4,166
```

同じトランザクションを複数のピアが持ってきた場合、**最初の1つにだけ課金する**。
ブロックに入った、追い出された、期限が切れた項目は勘定から外れる。

これで、攻撃者が何アドレス持っていようと、
**1つの勘定が取れるのはメンプールの 1/24** になる。
もっと取るには勘定を増やすしかない。

### 6.2 課金の宛先

勘定の単位を何にするかで、この設計は成立も破綻もする。

| 候補           | 結果                             |
| ------------ | ------------------------------ |
| 送信者アドレス      | ❌ タダで無限に作れる。§2 の誤り             |
| Node ID      | ❌ タダで無限に作れる。アドレスと同じ            |
| 生きている接続      | ❌ 切断・再接続で勘定がリセットされる            |
| **IP プレフィックス** | ⭕ 買わなければ増えない                |

**IP プレフィックスに課金する。** 切断しても勘定は残るので、
接続を張り直して枠を空けることはできない。

勘定は最後の項目が消えるまで保持する。

### 6.3 プレフィックスの長さ

**IP アドレス単位で数えてはいけない。IPv6 で即座に破られる。**

一般的な家庭回線にも /64 が配られる。
アドレス単位で数える実装は、IPv6 の攻撃者に対して
**1兆8千億個の勘定**を許すことになる。これは無制限と同じである。

| 種別   | 数える単位 | 同一単位からの接続 |
| ---- | ----- | --------- |
| IPv4 | /24   | 2         |
| IPv6 | /64   | 2         |
| IPv6 | /48   | 4         |

IPv6 は2段で数える。/64 は1契約、/48 は1拠点におおむね対応する。

ループバックと私設アドレスはこの制限の対象外とする
（同一マシン上の複数ノードは正当な構成である）。

### 6.4 接続枠の多様性

上限だけでは、攻撃者が inbound 16 枠を全部埋めて
**正直なピアを締め出す**ことができる。メンプールは守れてもノードが孤立する。

* inbound 16 枠のうち **4 枠を新規プレフィックス用に予約**する。
  既に枠を持つプレフィックスからの接続は、この4枠を使えない
* 枠が埋まっているとき、新規の接続要求は**最も素行の悪いピアを切って**受け入れる。
  スコアが同じなら最も古い接続を切る
* outbound 8 枠は攻撃者が触れない。こちらから選んで繋ぐため

outbound が攻撃者の手の届かない場所にあることは重要である。
inbound を全部取られても、チェーンの供給元は残る。

## 7. ピア単位の流量

時間あたりの上限。**既存のものは変えない。**

| 資源              | 上限        | 状態     |
| --------------- | --------- | ------ |
| メッセージ           | 100/秒     | 実装済み   |
| トランザクション        | 10/秒      | 実装済み   |
| 帯域              | 1 MiB/秒   | **未実装** |
| `GetData` の項目数  | 50/秒      | **未実装** |

`GetData` に専用の上限を置くのは、**それだけがディスクを読む**ためである。
1メッセージに 500 件（`MAX_INVENTORY`）入れられ、
メッセージは 100/秒 通るので、現状は毎秒 50,000 件のブロック読み出しを
要求できる。他のメッセージと同じ勘定で数えるべきではない。

## 8. 入場規則

以下は spam 対策ではなく、**正しさ**のためにある。
実装されていないので書いておく。

### 8.1 実効状態

```text
effective_nonce(S)   = state.nonce(S) + (メンプール内の S 発 tx の件数)
effective_balance(S) = state.balance(S) − Σ(メンプール内の S 発 tx の amount)
```

確定状態だけで見ると、同じ送信者の2件目が常に弾かれるか、
合計残高を超える組を受け入れてしまう。どちらも正しくない。

### 8.2 検査の順序

**安い検査から順に行う。順序はポリシーの一部である。**

| #  | 検査                           | 費用        |
| -- | ---------------------------- | --------- |
| 1  | 長さ                           | 定数        |
| 2  | 復号                           | 定数        |
| 3  | メンプールに同一ハッシュ                 | ハッシュ表1回   |
| 4  | 持ち込んだ勘定の枠に空きがあるか（§6.1）       | 表1回       |
| 5  | 送信者の口座が存在し、残高 > 0            | 状態1回      |
| 6  | `nonce == effective_nonce`   | 状態1回      |
| 7  | `amount ≤ effective_balance` | 状態1回      |
| 8  | **署名の検証（BIP-340 Schnorr）**   | **≒50µs** |
| 9  | グローバル上限（満杯なら §10）            | 定数        |

**署名検証を最後に置く。** 状態の参照はハッシュ表1回、
署名検証はその1000倍近く高い。
残高を持たない口座からのトランザクションは、署名を検証する前に落ちる。

現在の実装は逆で、[`lib.rs`](../crates/chroma-p2p/src/lib.rs) の
`MessageType::Tx` は署名を検証してから `add_transaction` を呼ぶ。

順序を入れ替えても安全性は変わらない。4〜7 が読むのは
そのトランザクションが自称する送信者の**公開情報**だけであり、
署名を先に見なくても漏れるものが無い。
署名の通らないものが受理されないことは 8 が保証する。

### 8.3 送信者ごとの保留件数に上限は設けない

§2 のとおり、口座を軸にした上限は口座を増やすだけで回避される。
効果が無い規則を置くと、それがあるから安全だと錯覚させる分だけ有害である。

1口座がメンプールを埋めることは §6.1 の枠が防ぐ。
**何アドレスから送られようと、1つの勘定は 4,166 件しか持てない。**

## 9. 合意側の床

ここだけは合意規則である。

**1つの送信者は、1ブロックに2件までしか入れられない**
（`MAX_TXS_PER_SENDER_PER_BLOCK`、実装済み）。

これまでの節は全てポリシーであり、従わないノードを罰する手段がない。
手数料収入が無いので、採掘者が従う動機も無い。
この規則だけは**違反したブロックが全ノードに拒否される**ため、
敵対的な採掘者に対しても成立する。

口座を分割すれば回避できるので、spam 対策としては弱い。
狙いは「1口座がブロックを占領しない」という床であって、
攻撃者の総量を縛ることではない。

## 10. 満杯のとき

`MAX_MEMPOOL_TXS` に達したら、エラーを返すのではなく**追い出す**。
現在の実装は満杯でエラーを返すため、先に入った者が居座り、
後から来た正当なトランザクションが入れない。

追い出す対象は、**枠を最も多く使っている勘定**（§6.1）の、
その勘定の中で最も新しい項目とする。

* 勘定は IP プレフィックスなので、口座を分割しても比は変わらない
* 新しい側から削るのは、nonce の列に穴を空けないため
* 新しく入るものがこの基準で最下位なら、追い出さずにそれを拒否する

## 11. 期限切れ

`MempoolEntry::added_at` に実際の時刻を入れ（現在は 0 固定）、
`MEMPOOL_EXPIRY_SECS` を超えた項目を落とす。1時間を提案する。

手数料が無いので「安すぎて永久に入らない」項目は存在しないが、
送信者の nonce が別の経路で進んだものは永久に入らない。
それを抱え続ける理由がない。

## 12. 攻撃者から見るとどうなるか

三層を全部同時に破る必要がある。数字を入れる。

### 12.1 メンプールを埋める

| 必要なもの        | 量                               |
| ------------ | ------------------------------- |
| 占有したい枠       | 100,000 件                       |
| 1勘定あたりの枠     | 4,166 件（§6.1）                   |
| **必要な勘定数**   | **24**                          |
| 1勘定あたりの接続    | 2（§6.3）                         |
| **必要な IP プレフィックス** | **12 個の /24**              |
| 取れる接続        | inbound 16 のうち、新規枠4を除く 12（§6.4） |
| **実際に取れる枠**  | **12 × 4,166 = 約 50,000 件（半分）** |

outbound 8 枠には触れないので、**メンプールの半分が上限**である。

### 12.2 それでも埋まらない

流量の側を見ると、もっとはっきりする。

```text
注ぎ込める速度 = 16 ピア × 10 tx/秒 =   160 tx/秒
ブロックが抜く速度 = 7,943 件 ÷ 10 秒 =   794 tx/秒
```

**抜ける速度が注げる速度の 5 倍ある。**
攻撃者はメンプールを満たすどころか、採掘に追いつかれる。
100,000 件を注ぐには、全枠を取った上で 10 分以上かかり、
その間ずっとブロックが抜き続ける。

### 12.3 残高も要る

さらに、注ぐ 100,000 件はすべて実在の残高に裏打ちされていなければならない（§8）。
残高は採掘するか受け取るかでしか得られない。

### 12.4 まとめ

攻撃者が必要とするもの:

* 12 個以上の /24（または IPv6 の /64）
* 全 inbound 枠の占有（正直なピアと競合しながら）
* 10 分以上の継続
* 100,000 件分の残高
* そして得られるのは、メンプールの半分を一時的に埋めることだけ

**これは割に合わない。** 手数料なしで達成できる水準として、これで足りる。

## 13. 未解決事項

### 13.1 Reorg で戻るトランザクション

ブロックが巻き戻ると、そこにあったトランザクションはメンプールに戻すべきである。
現在の実装はそれをしていない。

戻す場合、それは誰の勘定に付くのか。
持ち込んだピアはもう繋がっていないかもしれない。
**戻る項目は勘定の対象外とする**のが素直に見えるが、
それを悪用する経路がないかは検討していない。

### 13.2 プレフィックス長の妥当性

/24 と /64 は慣例に沿った値であり、実測に基づくものではない。
共有回線（キャリアグレード NAT、大学、企業）の背後にいる
正当な利用者が、同じ勘定に押し込められる可能性がある。

### 13.3 RPC 経由の投入

§7 はピア接続の話である。RPC から投入されるものは別の経路であり、
[`RPC.md`](RPC.md) の制限が担当する。
両者の合計に対するグローバル上限は §5 が押さえるが、
RPC の制限と P2P の制限を独立に設けてよいかは、
RPC を実装する段で確認する。
