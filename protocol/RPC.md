# Chroma RPC 仕様 草案 v0.3-draft

> これは草案である。SPEC §13 が「RPC/API仕様」を未解決事項として残しており、
> このファイルはその埋め方の提案にあたる。実装は存在しない。
> 確定するまで、ここに書かれた内容は互換性を約束しない。

## 1. 位置づけ

RPC はプロトコルの一部ではない。ノード同士の合意には一切関与せず、
ノードの外側にいるソフトウェアが、動いているノードに問い合わせるための口である。
したがって RPC を実装しないノードも、完全な Chroma ノードである。
RPC の有無・内容がノード間で食い違っても、チェーンは何の影響も受けない。

現在の CLI は RPC を使わない。ピアとして Noise でノードに接続し、
`GetChainInfo` / `GetAccount` を投げている
（[`crates/chroma-cli/src/main.rs`](../crates/chroma-cli/src/main.rs) の `NodeClient`）。
RPC が要るのは、Rust と Noise 実装を持たない第三者のソフトウェア
—— ブロックエクスプローラ、取引所、他言語のウォレット —— を繋ぐときである。

## 2. バージョニングと適合性

### 2.1 バージョン

RPC は SPEC のバージョンとも、ノードの実装バージョンとも独立に版を持つ。
`chroma_getNodeInfo` が返す3つのバージョンは別物である。

| フィールド              | 何の版か                    |
| ------------------ | ----------------------- |
| `version`          | ノード実装の版。RPC の互換性を意味しない  |
| `protocol_version` | P2P プロトコルの版。RPC とは無関係   |
| `rpc_version`      | **この文書の版。RPC の互換性はこれのみが決める** |

`rpc_version` は `"MAJOR.MINOR"` の文字列とし、両者とも先頭ゼロなしの10進整数とする。
パッチ番号は持たない。文書の版（`v0.3-draft`）と `rpc_version`（`"0.3"`）は同じ数を指す。

### 互換性の定義

* **MINOR の増加は後方互換。** 認められるのは、メソッドの追加、
  応答へのフィールド追加、省略可能な引数の追加のみ
* **MAJOR の増加は非互換。** 既存フィールドの削除・改名・型変更・意味変更、
  メソッドの削除・改名、エラーコードの意味変更を含む
* **`MAJOR` が `0` の間は、MINOR の増加も非互換でありうる。**
  これは例外規定ではなく、0.x とはそういうものである。
  安定を必要とする実装は 1.0 を待つこと

同一 MAJOR の中で、メソッド名・エラーコード・`data.reason` の識別子は意味を変えない。
一度公開した識別子は、MAJOR が変わるまで再利用もしない。

### クライアントの規則

クライアントは最初に `chroma_getNodeInfo` を呼び、`rpc_version` を読む。
自分が想定する版を `EXPECTED` として、

| 条件                        | 取るべき動作                       |
| ------------------------- | ---------------------------- |
| MAJOR が違う                 | 接続を中止する。推測で続けない              |
| MAJOR が同じ、MINOR がノードのほうが低い | ノードに無いメソッドがありうる。`-32601` を扱う |
| MAJOR が同じ、MINOR がノードのほうが高い | そのまま使ってよい。知らないものは無視する        |

**クライアントは知らないフィールドを無視しなければならない。**
これを守らないクライアントは MINOR の増加で壊れる。
知らないエラーコードは、`code` の符号だけを見て失敗として扱う。

版の交渉機構は設けない。`Accept-Version` のようなヘッダも持たない。
ノードは1つの版だけを話し、クライアントがそれに合わせる。

### 2.2 スキーマ

正規のスキーマは [OpenRPC](https://open-rpc.org/) 文書として
`protocol/rpc/openrpc.json` に置く。このファイルと OpenRPC 文書が食い違った場合、
**OpenRPC 文書を正とする**。散文は意図を説明するためにあり、
型の定義はスキーマが持つ。

### 2.3 適合性テスト

適合性テストは `protocol/rpc/conformance/` に、
要求と期待される応答の対として置く。実装がこれを全て通ることを RPC 適合の条件とする。
テストは少なくとも次を含む。

* 各メソッドの正常系
* 各エラーコードを1つ以上発生させる要求
* 認証なし・不正トークン・不正な `Host` の拒否
* 本文サイズ上限、バッチ上限、ページ上限の境界値
* 数値表現（先頭ゼロ、`+` 符号、u64 超過）の拒否

### 2.4 値の出どころ

**この文書はプロトコルの値を定義しない。** トランザクションの大きさ、
ブロックの上限、単位の換算、genesis の target といった値は
SPEC と [`chroma-core/src/constants.rs`](../crates/chroma-core/src/constants.rs)
が定めるものであり、この文書はそれを名前で参照する。

| 値                | 出どころ                              |
| ---------------- | --------------------------------- |
| トランザクションの大きさ     | `Transaction::SERIALIZED_SIZE`    |
| ブロックヘッダの大きさ      | `BlockHeader::SERIALIZED_SIZE`    |
| ブロックの上限          | `MAX_BLOCK_SIZE`                  |
| メンプールの上限         | `MAX_MEMPOOL_TXS`, `MAX_MEMPOOL_SIZE` |
| 単位の換算            | `UNITS_PER_CHR`                   |
| 最大供給量            | `MAX_SUPPLY_UNITS`                |
| target の上下限      | `DEFAULT_MAX_TARGET`, `DEFAULT_MIN_TARGET` |

この文書に現れる具体的な数字（264文字、7,900件など）は、
上の値から導いた**説明のための例**であって、定義ではない。
**食い違った場合は常に SPEC と定数を正とし、この文書を直す。**

hex の長さは常に「対応するバイト数の2倍」として定める。
定数が変われば hex の長さも自動的に変わる。この文書はその関係だけを定義する。

## 3. 有効化と待受

**RPC は既定で無効である。既定のポートも既定の待受アドレスも存在しない。**

有効化は `--rpc-listen <addr:port>` を明示したときに限る。この引数に既定値はなく、
省略した場合 RPC は起動しない。ポート番号は利用者が書く。

慣例として **8332**（P2P の 8333 の1つ下）を推奨するが、これは既定値ではない。
「既定で無効」と「既定ポート」は両立しないため、
推奨値として文書に書くにとどめ、実装は既定値を持たない。

### 3.1 ループバック以外への待受

`--rpc-listen` にループバック以外のアドレスを与えた場合、
ノードは **`--rpc-allow-external` が併せて与えられない限り起動を拒否する**。
拒否時は理由を述べて終了する。

これは事故防止のためであって、`--rpc-allow-external` を安全にするものではない。
外部公開する場合、運用側は次を満たさなければならない。

* TLS を終端するリバースプロキシを前段に置く
* プロキシからノードへはループバックで繋ぐ
* ノード自身は TLS を実装しない（鍵と証明書の管理をノードに持ち込まない）

**ノードは平文 HTTP しか話さない。** これは仕様であり、制限ではない。
TLS の設定・更新・失効を暗号通貨ノードの責務にしないための選択である。

## 4. セキュリティ

RPC ポートはノードが乗り取られる古典的な入口である。
`0.0.0.0` に晒された JSON-RPC から資金が抜かれた事例は数え切れない。
そのため次を仕様として固定する。

* 既定で無効（§3）
* **ノードは秘密鍵を持たない。送金メソッドを設けない**
* 認証は本文を読む前に済ませる（§4.2）

2点目が最も重要である。`sendtoaddress` に相当するメソッドは存在せず、
署名は必ずクライアント側で行う。RPC は署名済みトランザクションを受け取るだけである。
これにより、RPC が漏れても盗めるものがない。

### 4.1 認証トークン

| 項目     | 値                                    |
| ------ | ------------------------------------ |
| 生成     | ノード起動時、ファイルが無ければ生成                   |
| 長さ     | 32バイト（CSPRNG）                        |
| 表現     | 小文字 hex 64文字                         |
| 保存先    | `<data-dir>/rpc_token`               |
| パーミッション | `0600`（Unix）。node_key と同じ扱い          |
| 送り方    | `Authorization: Bearer <token>`      |

ファイルが既に存在する場合は読み込んで使う。生成し直さない。
ローテーションは、ファイルを削除してノードを再起動することで行う。
トークンの寿命・失効・複数トークンは v0.2 では扱わない。

比較は**定数時間で行う**。長さが違う場合も、比較の前に打ち切ってはならない。
`Authorization` ヘッダが無い、形式が違う、値が一致しない、のいずれも
**同一の応答**（`401`、本文は固定文字列）を返す。区別してはならない。

ループバックからの接続を認証免除にはしない。
同じマシン上の別のプロセス（ブラウザを含む）は攻撃者になりうる。

### 4.2 処理順序

要求は次の順で処理する。**この順序は仕様である。**

1. メソッドが `POST` か（違えば `405`）
2. パスが `/` か（違えば `404`）
3. `Host` ヘッダの検査（§4.3）（不正なら `403`）
4. `Origin` ヘッダの検査（§4.3）（存在すれば `403`）
5. `Content-Length` の存在と上限（§5.2）（超過なら `413`、欠落なら `411`）
6. `Content-Type` が `application/json`（違えば `415`）
7. **認証**（§4.1）（不一致なら `401`）
8. 本文の読み込み
9. JSON の解析（失敗なら JSON-RPC `-32700`）
10. バッチ上限の検査（§6.2）
11. メソッドの実行

**認証は本文の読み込みより前**に置く。認証されていない相手に
JSON パーサを踏ませない。本文を読まずに `401` を返す実装は、
接続を閉じる前に `Connection: close` を付けてよい。

### 4.3 DNS リバインディング対策

ローカルの RPC に対する典型的な攻撃は、利用者のブラウザを踏み台にするものである。
攻撃者のページが自分のドメインを `127.0.0.1` に解決させ、
そのページの JavaScript から RPC を叩く。ループバック限定も認証も、これには効かない
（トークンは効くが、ブラウザ経由でトークンを持ち出された場合は効かない）。

対策として次を課す。

* **`Host` ヘッダを検査する**（規則は下記）
* **`Origin` ヘッダが存在する要求は、値によらず拒否する。**
  RPC はブラウザから直接叩かれることを想定していない
* **CORS ヘッダは一切返さない。** プリフライト（`OPTIONS`）には `405` を返す

ブラウザから使いたい場合は、アプリケーション側のサーバを経由させる。
これは制限であって、緩和する設定は設けない。

#### `Host` の規則

要求の `Host` は、次を**全て**満たさなければならない。満たさなければ `403`。

1. ヘッダが存在する（無ければ `400`）
2. **IP リテラルである。** ホスト名は `localhost` を含めて全て拒否する
3. IPv6 は角括弧で囲まれている（`[::1]:8332`）
4. **ポートが明記され、`--rpc-listen` のポートと一致する。**
   省略は拒否する。RPC は 80/443 で待ち受けないので、
   ポートが省略された `Host` は正しい要求ではない
5. IP 部分が**許可アドレスの集合に含まれる**（下記）

**許可アドレスの集合**は、`--rpc-listen` の与え方で決まる。

| `--rpc-listen` の指定 | 許可アドレス                    |
| ------------------ | ------------------------- |
| 具体的な IP（`127.0.0.1:8332`） | その IP ただ1つ            |
| ワイルドカード（`0.0.0.0:8332`, `[::]:8332`） | **`--rpc-host` で明示された IP のみ** |

**ワイルドカードに待ち受ける場合、`--rpc-host <ip>[,<ip>…]` が無ければ起動を拒否する。**
待ち受けアドレスから許可 `Host` を導けないためであり、
「全て許可」に落とすと DNS リバインディング対策が消える。

`--rpc-host` に与えられるのは IP リテラルのみで、ホスト名は受け付けない。
リバースプロキシを前段に置く構成では、プロキシがループバックへ繋ぐため
`--rpc-listen 127.0.0.1:8332` で足り、ワイルドカードは不要である。
その場合プロキシは `Host` を `127.0.0.1:8332` に書き換える。

## 5. HTTP

### 5.1 要求

| 項目           | 値                              |
| ------------ | ------------------------------ |
| メソッド         | `POST` のみ                      |
| パス           | `/` のみ                         |
| Content-Type | `application/json`             |
| 文字符号化        | UTF-8 固定（`charset` 指定は無視）      |

### 5.2 上限

| 項目            | 上限        | 超過時          |
| ------------- | --------- | ------------ |
| 要求本文          | 1 MiB     | `413`        |
| ヘッダ全体         | 8 KiB     | `431`        |
| ヘッダ1行         | 4 KiB     | `431`        |
| ヘッダ数          | 64        | `431`        |
| 応答本文          | 8 MiB     | `-32004`（§10） |
| 同時接続数         | 16        | 受理せず切断       |
| 1接続あたり要求数     | 100       | 以後 `Connection: close` |

`Content-Length` の無い要求は `411` で拒否する。
チャンク転送符号化は受け付けない。

### 5.3 タイムアウト

| 局面           | 上限   | 超過時   |
| ------------ | ---- | ----- |
| ヘッダ受信完了まで    | 5秒   | 切断    |
| 本文受信完了まで     | 10秒  | `408` |
| メソッド実行       | 30秒  | `-32005` |
| 応答送信完了まで     | 30秒  | 切断    |
| キープアライブ待機    | 30秒  | 切断    |

### 5.4 レート制限

* 接続元 IP ごとに **毎秒 50 要求**。バッチは要素数だけ数える
* 超過した要求には `429` と `Retry-After: 1` を返す
* 認証に失敗した接続元は **5回で60秒の遮断**とする

`chroma_sendRawTransaction` には、これとは別に**専用の上限**を置く。
他のメソッドが読み取りで終わるのに対し、これだけが
署名検証を走らせ、メンプールの枠を消費し、ピアへの告知を発生させるためである。

| 範囲            | 上限     |
| ------------- | ------ |
| 接続元 IP ごと     | 5/秒    |
| ノード全体（RPC 合計） | 20/秒   |

**全体の上限が要るのは、IP ごとの上限だけでは足りないためである。**
RPC を外部公開した場合、IP を増やせば IP ごとの上限は意味を失う。
P2P 側が 1ピアあたり 10/秒 で縛られているのに、
RPC が無制限では、そちらが最も広い入口になってしまう。

超過は `429` ではなく `-32003` `rate_limited` を返す。
呼び出し側から見ると、これはトランザクションが受理されなかったという結果である。

制限値は実装が設定で変更してよい。既定値をこの表に定める。

## 6. JSON-RPC

規格は JSON-RPC 2.0 に従う。以下はその上での取り決めである。

### 6.1 `id` と通知

* `id` は文字列・数値・`null` を受け入れる。小数を含む数値は `-32600` で拒否する
* `id` を持たない要求（通知）は実行するが応答を返さない。
  ただし `chroma_sendRawTransaction` を通知として送ってはならない
  （結果を確認できないため）。実装は通知でも受理してよいが、推奨しない

### 6.2 バッチ

* 1バッチあたり **20要素**まで。超過は `-32600`（バッチ全体を拒否）
* 空配列は `-32600`
* バッチの入れ子は認めない
* 各要素は独立に処理し、独立に成功・失敗する。**バッチは原子的ではない**
* 全要素が通知の場合、応答本文を返さず `204` を返す

### 6.3 引数の形式

`params` は**位置指定の配列と、名前付きのオブジェクトの両方**を受け入れる。

```json
{"jsonrpc":"2.0","id":1,"method":"chroma_getBlockByHeight","params":[486,1]}
{"jsonrpc":"2.0","id":1,"method":"chroma_getBlockByHeight","params":{"height":486,"verbosity":1}}
```

**クライアントは名前付きを使うことを推奨する。**
将来の MINOR で引数が追加された場合、位置指定は末尾追加しか受け付けられないが、
名前付きなら順序に依存しない。

`params` の省略は空配列と同じ。省略可能な引数に `null` を渡すのは省略と同じ。
知らない名前の引数は `-32602` で拒否する（黙って無視しない）。

### 6.4 カーソル

一覧を返すメソッド（`chroma_getMempool`、`chroma_getPeerInfo`）は
`cursor` を取り、`next_cursor` を返す。

* **カーソルは不透明である。** 中身に意味を持たせず、クライアントは解析してはならない
* 表現は base64url（パディングなし）の文字列、**128文字以下**
* 値は**それを発行したノードでのみ有効**。他のノードに渡してはならない
* **ノードの再起動をまたいで有効ではない**
* `null` または省略は「先頭から」を意味する
* `next_cursor` が `null` なら、そのノードの視点では続きがない
* 解釈できないカーソルは `-32602` `"bad_cursor"`。
  黙って先頭から返してはならない（クライアントが無限ループに陥る）

**カーソルは位置を保証しない。** 一覧の対象（メンプール、ピア）は
ページを送っている間にも変化する。カーソルは「前回の続きらしき場所」であって、
スナップショットではない。**ページを跨いだ重複と欠落は起こりうる**（§8.1）。

一貫した一覧が必要な用途に、この API を使ってはならない。

## 7. 型の表現

| 種類            | 表現            | 例                    |
| ------------- | ------------- | -------------------- |
| ハッシュ          | 64桁 hex       | `"d1c3ba…"`          |
| 公開鍵           | 64桁 hex       | `"752b…"`            |
| アドレス          | bech32 文字列    | `"chr1ddmp…"`        |
| 金額・供給量・nonce  | **10進文字列**    | `"31000000"`         |
| 高さ            | 数値（u32）       | `486`                |
| bits          | hex 文字列       | `"0x1f400000"`       |
| 難易度           | 数値（浮動小数）      | `10.0`               |
| 時刻            | 数値（Unix秒、u64） | `1757155200`         |

### 7.1 hex

**出力は常に小文字、接頭辞なし、固定長。**
ハッシュと公開鍵は必ず64文字であり、短縮も先頭ゼロの省略もしない。

**入力は大文字小文字を区別しない**が、長さは厳密に検査する。
`0x` 接頭辞の付いた hex は `-32602` で拒否する
（`bits` だけは接頭辞付きであり、これが唯一の例外である。§7.4）。
hex でない文字が含まれる場合も `-32602`。

### 7.2 整数の文字列表現

u64 に収まる値を、次の形でのみ表す。

* 基数10、`0`-`9` のみ
* 先頭ゼロを付けない（`0` 自身を除く）
* 符号を付けない（`+`、`-` とも不可）
* 空白を含めない
* 指数表記を使わない

**出力はこの正規形で行う。入力もこの正規形のみを受け入れ、
それ以外は `-32602` で拒否する。** `"007"`、`"+7"`、`"7 "`、`"7.0"`、`"7e0"` は全て不正である。
u64 の範囲（0 〜 18446744073709551615）を超える値も `-32602`。

金額を文字列にするのは、最大供給量が 100,000,000,000,000 units であり、
JavaScript の `Number.MAX_SAFE_INTEGER`（2⁵³−1 = 9007199254740991）を超えるためである。
数値で返すと、JSON をパースした時点で静かに桁が落ちる。

### 7.3 通貨単位

**RPC は常に units で表す。CHR では表さない。**
1 CHR = 1,000,000 units（10⁻⁶）であり、この換算は表示層の責務とする。
浮動小数で金額を表すフィールドは存在しない。
フィールド名に単位を含めない代わりに、この節をもって全ての金額を units と定める。

### 7.4 bits と難易度

`bits` は `"0x"` 接頭辞付きの8桁 hex 文字列で表す（例 `"0x1f400000"`）。
これは compact target の符号化そのものであり、
**PoW を検証するクライアントはこの値を使わなければならない。**

`expected_hashes_log2` は `bits` から導かれる派生値で、
`log2(2²⁵⁶ / target)` を倍精度浮動小数で表す。**表示のためだけにある。**
この値を使って PoW を検証してはならない。

整数に丸めないのは、丸めると差が消えるためである。
2^12.00 から 2^10.27 への変化は「2^12 → 2^10」と表示され実際より大きく見え、
2^10.00 から 2^10.99 への変化は「変化なし」に見える。

草案中の例に使う値の対応を示す。

| bits           | target        | expected_hashes_log2 | 由来               |
| -------------- | ------------- | -------------------- | ---------------- |
| `"0x1f100000"` | 2²⁴⁴          | 12.0                 | `GENESIS_TARGET_BITS` |
| `"0x1f400000"` | 2²⁴⁶          | 10.0                 | `DEFAULT_MAX_TARGET`（最も易しい） |

`0x1f400000` は mantissa `0x400000` = 2²², exponent `0x1f` = 31 なので
target = 2²² × 256²⁸ = 2²⁴⁶、2²⁵⁶ / 2²⁴⁶ = 2¹⁰ である。

### 7.5 アドレス

出力は bech32 文字列、小文字。入力は大文字小文字を区別しないが、
bech32 の規定どおり**大小の混在は拒否する**。

**現在、HRP は全ネットワークで `chr` である**
（[`constants.rs`](../crates/chroma-core/src/constants.rs) の `ADDRESS_HRP`）。
したがってアドレス文字列だけを見て mainnet と testnet を区別することはできない。
RPC はアドレスの HRP からネットワークを判定してはならず、
**ノード自身のネットワークに属するアドレスとして解釈する**。

これはアドレス形式の問題であって RPC で修正できるものではない。
ネットワークごとに HRP を分ける案は §11 に未解決事項として挙げる。

### 7.6 高さ

高さは u32 の数値で表す。`0` は genesis を指す。

* 小数、負数、文字列は `-32602`
* u32 を超える値は `-32602`
* 範囲としては妥当だが先端を超える高さは `-32001`（見つからない）

## 8. 一貫性

### 8.1 スナップショット

**1回のメソッド呼び出しは、単一のチェーン状態から応答しなければならない。**
高さを読んでから先端ハッシュを読む間にブロックが着信し、
高さ486・先端は487のもの、という応答を返してはならない。
実装はメソッドの入口でチェーン状態の読み取りロックを1度だけ取り、
応答の組み立てまで保持する。

**バッチの要素間では一貫性を保証しない。**
バッチの2要素が異なる先端を見ることはありうる。
一貫した複数の値が必要なら、それらを1つのメソッドで返す。

### 8.2 応答に含める先端

`chroma_getChainInfo` 以外のメソッドも、応答に
`tip`（そのとき見ていた先端ハッシュ）と `tip_height` を含める。
クライアントは複数の応答を突き合わせるときに、これで整合を判定できる。

### 8.3 同期中の扱い

初期同期中は、答えられるものと答えられないものがある。

| メソッド                      | 同期中の挙動                     |
| ------------------------- | -------------------------- |
| `chroma_getNodeInfo`      | 常に答える                      |
| `chroma_getChainInfo`     | 答える。`"syncing": true` を含める |
| `chroma_getPeerInfo`      | 答える                        |
| `chroma_getHeader(s)`     | 持っている範囲について答える             |
| `chroma_getBlockBy*`      | 持っていれば答える。無ければ `-32001`    |
| `chroma_getAccount`       | **`-32002`**（同期中で答えられない）   |
| `chroma_getMempool`       | 答える                        |
| `chroma_sendRawTransaction` | **`-32002`**              |

`chroma_getAccount` を拒否するのは、同期途中の残高が
「間違っている」ではなく「過去のある時点のもの」だからである。
それを現在の残高として表示させるより、答えないほうがよい。

## 9. メソッド

全メソッドは §8.2 のとおり `tip` と `tip_height` を含む
（`chroma_getNodeInfo` を除く。ノード情報はチェーンに依らない）。

### 9.1 `chroma_getChainInfo`

引数なし。

```json
{
  "network": "chroma-mainnet",
  "height": 486,
  "tip": "5fd3a3d9f0a85546670c3b43fef7522eeb0774f913abe78aa2fbe3759ef146c2",
  "tip_height": 486,
  "genesis": "…",
  "bits": "0x1f400000",
  "expected_hashes_log2": 10.0,
  "supply": "486000000",
  "pow": "randomx",
  "syncing": false
}
```

### 9.2 `chroma_getAccount`

`{"address": "chr1ddmplpspsertlny5n5vytfps7dc5w00edm00pd"}`

```json
{ "address": "chr1ddmp…", "exists": true, "balance": "31000000", "nonce": "0",
  "tip": "…", "tip_height": 486 }
```

存在しない口座はエラーではなく `"exists": false` と `"0"` を返す。
チェーンにとって「残高0の口座」と「知らない口座」は同じものである。

### 9.3 `chroma_getBlockByHeight` / `chroma_getBlockByHash`

`{"height": 486, "verbosity": 1}` / `{"hash": "5fd3…", "verbosity": 1}`

`verbosity` の既定は `1`。

| 値   | 返すもの                    |
| --- | ----------------------- |
| `0` | 生ブロックの hex 文字列          |
| `1` | ヘッダ各フィールド + tx ハッシュの配列  |
| `2` | ヘッダ各フィールド + tx を展開したもの  |

```json
{
  "hash": "5fd3…",
  "height": 486,
  "version": 1,
  "previous_hash": "…",
  "state_root": "…",
  "tx_merkle_root": "…",
  "timestamp": 1757155200,
  "bits": "0x1f400000",
  "nonce": "8123441",
  "size": 256,
  "tx_count": 1,
  "confirmations": 1,
  "on_active_chain": true,
  "transactions": ["…"],
  "tip": "…",
  "tip_height": 486
}
```

**応答サイズ。** 1ブロックが含みうる tx の件数は
`MAX_BLOCK_SIZE / Transaction::SERIALIZED_SIZE` である
（現在の定数では 1 MiB ÷ 132 バイトで 7,900 件強。§2.4）。
`verbosity: 2` はこれを JSON に展開するため、応答が §5.2 の 8 MiB を超えうる。
超える場合は結果を切り詰めず、**`-32004` を返す**。
クライアントは `verbosity: 1` で tx ハッシュを取り、必要な分だけ引く。

**非アクティブチェーンのブロック。**
`chroma_getBlockByHash` は、負けた枝のブロックも保持していれば返す。
その場合 `"on_active_chain": false`、`"confirmations": -1` とする。
`chroma_getBlockByHeight` は**アクティブチェーンのみ**を対象とする
（高さは負けた枝を一意に指せないため）。

**`confirmations`** は「先端の高さ − そのブロックの高さ + 1」とする。
先端自身は `1`。アクティブチェーン上にないブロックは `-1`。
Reorg でこの値の意味は変わりうるので、クライアントは
`tip` を併せて見ること。

### 9.4 `chroma_getHeader` / `chroma_getHeaders`

`chroma_getHeader` — `{"height": 486}` または `{"hash": "5fd3…"}`。
どちらか一方を与える。両方または片方も無い場合は `-32602`。

`chroma_getHeaders` — `{"from_height": 400, "count": 100}`。
アクティブチェーン上の連続するヘッダを返す。

* `count` の既定は `100`、上限は `2000`。超過は `-32602`
* `from_height` が先端を超える場合は空配列（エラーではない）
* 返す件数が `count` に満たないことはありうる（先端に達した場合）

軽量クライアントが PoW を検証するための経路である。
ヘッダは固定長（`BlockHeader::SERIALIZED_SIZE`、現在 124 バイト）なので、
上限の 2000 件でも 250 KB 程度に収まる。上限はこの見積りから決めている。

### 9.5 `chroma_getMempool`

`{"limit": 500, "cursor": null}`

```json
{
  "count": 1200,
  "transactions": ["…", "…"],
  "next_cursor": "…",
  "tip": "…",
  "tip_height": 486
}
```

* `count` はメンプール全体の件数。`transactions` の長さではない
* `limit` の既定は `500`、上限は `2000`
* `cursor` と `next_cursor` の意味は §6.4 に定める
* **順序は「そのノードのメンプールに入った順」**とし、安定とはしない。
  メンプールは `MAX_MEMPOOL_TXS` 件まで入り、ページを跨ぐ間に増減する。
  **ページ送りの間に重複や欠落が起こりうる**（§6.4）
* 一貫した一覧が必要な場合はブロックに入るのを待つこと。
  メンプールは合意の対象ではなく、ノードごとに内容が違う

### 9.6 `chroma_sendRawTransaction`

`{"hex": "<署名済みトランザクションの hex>"}`

トランザクションは固定長である（`Transaction::SERIALIZED_SIZE`、§2.4）。
hex はその2倍の文字数ちょうどでなければならず、違えば `-32602`。
現在の定数では 132 バイト = 264 文字だが、正はあくまで定数の側である。

#### 実効状態（effective state）

**受理の判定は、確定状態ではなく実効状態に対して行う。**
実効状態とは、確定状態にメンプールの未確定分を重ねたものである。

```text
effective_nonce(S)   = state.nonce(S) + (メンプール内の S 発 tx の件数)
effective_balance(S) = state.balance(S) − Σ(メンプール内の S 発 tx の amount)
```

確定状態だけで判定すると、同じ送信者の2件目が常に弾かれるか、
あるいは合計残高を超える組を受け入れてしまう。どちらも正しくない。

#### 受理の条件

次を**この順に**検査し、最初に失敗したものを理由として返す。順序は仕様である。

| #  | 検査                                        | 失敗時                                    |
| -- | ----------------------------------------- | -------------------------------------- |
| 1  | hex の長さと文字種                               | `-32602`                               |
| 2  | 復号（フィールドの読み出し）                            | `-32003` `malformed`                   |
| 3  | **メンプールに同一ハッシュが在る**                       | **成功**（冪等。下記）                          |
| 4  | **索引があれば、既にブロックに在るか**                     | `-32003` `already_mined`               |
| 5  | 送信者の口座が存在し、残高 > 0                        | `-32003` `unfunded_sender`             |
| 6  | `nonce` < `effective_nonce`                | `-32003` `nonce_too_low`               |
| 7  | `nonce` > `effective_nonce`                | `-32003` `nonce_too_high`              |
| 8  | `amount` > `effective_balance`             | `-32003` `insufficient_balance`        |
| 9  | **署名の検証（BIP-340 Schnorr）**                | `-32003` `bad_signature`               |
| 10 | メンプール全体の容量                                | `-32003` `mempool_full`                |

送信者あたりの未確定件数に上限は設けない。
口座を軸にした上限は口座を増やすだけで回避されるためであり、
1つの送信元がメンプールを埋めることは
[`MEMPOOL.md`](MEMPOOL.md) §6.1 の枠が防ぐ。

**署名検証を最後に置く**のが要点である。3〜8 はハッシュ表と状態の参照で済み、
署名検証はその1000倍近く高い（1件およそ 50µs）。
残高を持たない口座からのトランザクションは、署名を検証する前に落ちる。

順序を入れ替えても安全性は変わらない。5〜8 が読むのは、
そのトランザクションが自称する送信者の**公開情報**
（`chroma_getAccount` で誰でも引ける）だけであり、
署名を先に見なくても漏れるものが無い。
署名の通らないものが受理されないことは 9 が保証する。

**このメソッドは、ノードのメンプールと同じ規則で判定しなければならない。**
規則の全体は [`protocol/MEMPOOL.md`](MEMPOOL.md) に定める。

**`already_mined` と nonce の関係。** 既に採掘されたトランザクションは、
送信者の nonce が進んでいるので、6 の `nonce_too_low` にも必ず該当する。
両者は排他ではなく、**4 が 6 より前にあることで決まる**。

ただし 4 は**索引を持つノードでしか行えない**（§11.1）。
索引が無ければ tx ハッシュからブロックを引けないためである。したがって、

* 索引のあるノード → `already_mined`
* 索引の無いノード → `nonce_too_low`

同じトランザクションに対して、**ノードによって理由が変わる**。
クライアントは `already_mined` と `nonce_too_low` を
**どちらも「このトランザクションはもう送れない」として扱わなければならない**。
`already_mined` が返らないことを、まだ採掘されていない証拠にしてはならない。

#### 冪等性

既にメンプールに同じトランザクションがある場合、
**エラーではなく成功を返す**。同じハッシュを返し、`"already_in_mempool": true` を添える。
再送は正常な操作であり、失敗として扱わない。

同じ nonce で**中身の違う**トランザクションは、`nonce_too_high` でも
`nonce_too_low` でもなく、7 で弾かれる（`effective_nonce` は既に進んでいる）。
手数料が無いため、置き換え（replace-by-fee）は存在しない。
**先に受理されたものが残る。**

#### 手数料が無いことと spam

Chroma に手数料は無いため、メンプールへの入場料も無い。
spam に耐える役目は、上の 5〜9 が負っている。
根拠と限界は [`protocol/MEMPOOL.md`](MEMPOOL.md) に述べる。

要点だけ繰り返すと、締め出す軸は**口座ではなく資源**である。
攻撃者が何アドレス持っていようと、それを1つのノードに流し込むには接続が要る。
グローバル上限・接続単位の割当・ピア単位の流量の三層で、
**1つの発信元がノードに注ぎ込める量**を縛る（MEMPOOL.md §3）。

**実装の現状。** [`chroma-p2p/src/mempool.rs`](../crates/chroma-p2p/src/mempool.rs) の
`add_transaction` は、いま**この節のどの検査も行っていない**。
重複ハッシュと全体の容量しか見ていない。
RPC だけ塞いでもピアから流し込まれるので、
**同じ規則をメンプール自身が P2P 経由の受信にも適用しなければ意味がない**。

**成功の意味。** 成功は「**このノードのメンプールに入った**」ことのみを意味する。

* ネットワークに伝播したことを意味しない
* 他のノードが受理したことを意味しない
* ブロックに入ることを意味しない
* 接続中のピアがゼロでも成功しうる

告知は受理後に行うが、その結果は応答に含めない。
伝播を確認したいクライアントは、`chroma_getBlockBy*` でブロックに入るのを見ること。

```json
{ "hash": "…", "already_in_mempool": false, "tip": "…", "tip_height": 486 }
```

### 9.7 `chroma_getPeerInfo`

`{"limit": 100, "cursor": null}`

```json
{
  "count": 1,
  "peers": [
    {
      "address": "60.151.51.203:8333",
      "node_id": "752b…",
      "direction": "outbound",
      "height": 486
    }
  ],
  "next_cursor": null,
  "tip": "…",
  "tip_height": 486
}
```

`limit` の既定は `100`、上限は `1000`。
`cursor` と `next_cursor` の意味は §6.4 に定める。
`node_id` は ed25519 公開鍵であり、秘密の値ではない（§9.8）。

### 9.8 `chroma_getNodeInfo`

引数なし。チェーンに依らない情報のみを返すため、`tip` を含めない。

```json
{
  "version": "0.1.0",
  "rpc_version": "0.2",
  "protocol_version": 1,
  "network": "chroma-mainnet",
  "node_id": "752b…",
  "noise_static_pubkey": "c611…",
  "peers": 1,
  "mining": true,
  "indexed": false,
  "uptime_secs": 3600
}
```

**鍵の区別。** ここで返す2つの鍵は、いずれも**公開鍵**であり、資金とは無関係である。

| 名前                    | 実体                  | 用途                     |
| --------------------- | ------------------- | ---------------------- |
| `node_id`             | ed25519 公開鍵         | ノードの身元。静的鍵への署名を検証する    |
| `noise_static_pubkey` | X25519 公開鍵          | Noise XK の静的鍵。接続に使う    |

どちらも `<data-dir>/node_key` に由来し、
**ウォレットの鍵とは別物である**。ウォレットの鍵はノードに存在しない（§4）。
`noise_key` という名は秘密鍵と紛らわしいため使わず、
`noise_static_pubkey` と綴る。

現在の実装では、X25519 の秘密鍵は ed25519 の種から導出される。
したがって `node_id` が同じノードは `noise_static_pubkey` も必ず同じであり、
**静的鍵だけを更新することはできない**。SPEC §10.1 はそれを認めているが、
実装はしていない。詳細は §11.5。

## 10. エラー

### 10.1 形

```json
{"jsonrpc":"2.0","id":1,
 "error":{"code":-32003,"message":"transaction rejected","data":{"reason":"bad_nonce"}}}
```

* **`code` と `data.reason` は安定である。** クライアントはこれで分岐する
* **`message` は安定ではない。** 人間向けであり、文言は予告なく変わる。
  クライアントは `message` を解析してはならない

### 10.2 コード

JSON-RPC 2.0 標準の `-32700`、`-32600`、`-32601`、`-32602`、`-32603` に加えて、
次を定義する。

| code     | 意味                         | `data.reason` の例                       |
| -------- | -------------------------- | -------------------------------------- |
| `-32001` | 見つからない                     | `block_not_found`, `header_not_found`  |
| `-32002` | 同期中で答えられない                 | `syncing`                              |
| `-32003` | トランザクション拒否                 | `nonce_too_low`, `rate_limited` ほか §9.6 の一覧 |
| `-32004` | 応答が大きすぎる                   | `response_too_large`                   |
| `-32005` | 実行がタイムアウトした                | `timeout`                              |
| `-32006` | この機能に必要な索引が無い              | `no_transaction_index`                 |

`-32602` の `data.reason` には、少なくとも `bad_cursor`（§6.4）を含む。

**`-32001` の粒度。** 「見つからない」を1つにまとめず、
`data.reason` で何が無いのかを区別する。

| reason               | 意味                          |
| -------------------- | --------------------------- |
| `block_not_found`    | そのハッシュのブロックを持っていない          |
| `height_above_tip`   | 高さは妥当だが先端より上                |
| `header_not_found`   | その高さ・ハッシュのヘッダを持っていない        |
| `not_on_active_chain` | 高さ指定でアクティブチェーン上に無い          |

口座は「見つからない」を返さない（§9.2）。

### 10.3 内部情報を出さない

`message` と `data` に次を含めてはならない。

* ファイルパス、データディレクトリの位置
* データベース（sled）の内部エラー文字列
* バックトレース、ソース位置、行番号
* ピアの IP アドレス（`chroma_getPeerInfo` の応答を除く）
* ホスト名、環境変数、ユーザ名

`data.reason` は**あらかじめ定義された識別子の集合**であり、
実行時に組み立てた文字列を入れない。
詳細はノードのログに書く。ログは運用者のものであり、RPC の利用者のものではない。

## 11. 未解決事項

### 11.1 トランザクション索引

`chroma_getTransaction`（tx ハッシュからの逆引き）を、この草案には含めていない。

引くには tx → ブロックの索引が要り、`chroma-storage` は現在それを持たない。
入れる場合は storage に索引を追加し、既存のチェーンを再インデックスする作業が伴う。
索引は state root にコミットされていないため合意の対象ではなく、
**ノードごとに有無が違ってよい**。

方針として次を提案する。

* 索引は `--index-transactions` で**任意有効化**とし、既定は無効
* tx 索引（tx→ブロック）と履歴索引（アドレス→tx）を**別フラグにしない**。
  片方だけ有効なノードがあると、クライアントが毎回能力を判定することになる
* `chroma_getNodeInfo` の `"indexed"` が唯一の判定材料とする
* 索引を持たないノードへの `chroma_getTransaction` は `-32006` とする

**着手の順序に1点だけ注意がある。** 索引は後から全ブロックを読み直して構築できるが、
それはブロックが全て残っている場合に限る。
**ブロックの剪定（pruning）を先に実装すると、再インデックスができなくなる。**
剪定より索引を先に決める。

### 11.2 アドレスのネットワーク識別

HRP が全ネットワークで `chr` であるため、アドレス文字列だけでは
mainnet 宛と testnet 宛を区別できない（§7.5）。
ネットワークごとに HRP を分ける（例: `chr` / `tchr`）ことは可能だが、
アドレス形式の変更であり SPEC の改訂を伴う。RPC 側では解決しない。

### 11.3 購読

ブロック着信やメンプール更新を待つ購読（WebSocket、Server-Sent Events）は
この草案に含めない。理由は、購読を入れると
接続の寿命・再接続時の取りこぼし・購読ごとの資源制限という、
要求応答とは別の設計課題が丸ごと増えるためである。

将来入れる場合は、この仕様の上に**別立ての文書**として設計する。
その際も、**この HTTP RPC は購読なしで完結したまま**とする。
ポーリングで足りる用途に購読を強制しない。

### 11.4 認証の拡張

トークンのローテーション、複数トークン、メソッドごとの権限
（読み取り専用トークンなど）は v0.2 では扱わない。
必要になるのは、ノードを複数の利用者で共有する場合である。

### 11.5 Noise 静的鍵の導出とローテーション

§9.8 で触れた点を、未解決事項として明示する。

**まずハンドシェイクの型について。** Chroma が使うのは XK であって XX ではない
（SPEC §10.2）。両者を混同しないよう、境界を書いておく。

* XK では responder の静的鍵は **pre-message**、すなわち initiator が
  接続前から知っている値である。ハンドシェイクの中で送られはしない
* SPEC §10.2 が message 2 の payload に載せる responder の proof は、
  **静的鍵の送信ではない**。既知の静的鍵を Node ID に結びつける署名であり、
  「この静的鍵は確かにこの Node ID のものだ」しか述べていない
* 静的鍵の秘密の所持は、message 1 の `es` を復号できたこと自体が証明している。
  proof はその上で身元を足すものであって、鍵交換には関与しない

したがって「両者が身元を交換するから XX ではないか」という読みは成り立たない。
交換しているのは身元であって、静的鍵ではない。矛盾があるのは型ではなく、
その静的鍵が**どこから来るか**のほうである。

SPEC §10.1 は「Static Key は Node ID を変えずに更新しうる」と述べ、
同時に「Static Key を Identity Key の種から導出することを認める」とも述べている。
**現在の実装は後者を選んでおり、その結果として前者ができない。**

```text
noise_secret = BLAKE3::derive_key("chroma noise static secret v1", identity_seed)
```

この導出は [`chroma-crypto/src/noise.rs`](../crates/chroma-crypto/src/noise.rs) にあり、
**SPEC には書かれていない**。したがって、

* 同じ `node_key` ファイルを別の実装に渡しても、同じ静的鍵にはならない。
  `node_key` の形式は現時点で相互運用可能ではない
* 静的鍵を変えるには種を変えるしかなく、種を変えれば Node ID も変わる。
  「Node ID を保ったまま静的鍵を更新する」経路が実装上存在しない

決めるべきことは2つある。

1. **導出を仕様に書くか、書かないか。**
   書くなら、文脈文字列と関数を SPEC §10.1 に含め、`node_key` の形式を
   相互運用可能にする。書かないなら、`node_key` は実装固有のファイルであると
   明記する
2. **ローテーションを実際に必要とするか。**
   必要なら、静的鍵の秘密を種から導出せず独立に保存する形に変える。
   不要なら、SPEC §10.1 の「更新しうる」という記述を実装に合わせて改める

なお、導出で使う2つの文脈文字列は紛らわしい。
署名対象は `"chroma-noise-static-key-v1"`（ハイフン）、
鍵導出は `"chroma noise static secret v1"`（空白）である。
別物であり、取り違えると相互運用できない静的鍵ができる。
