# Chroma RPC 仕様 草案 v0.1-draft

> これは草案である。SPEC §13 が「RPC/API仕様」を未解決事項として残しており、
> このファイルはその埋め方の提案にあたる。実装は存在しない。
> 確定するまで、ここに書かれた内容は互換性を約束しない。

## 1. 位置づけ

RPC はプロトコルの一部ではない。ノード同士の合意には一切関与せず、
ノードの外側にいるソフトウェアが、動いているノードに問い合わせるための口である。
したがって RPC を実装しないノードも、完全な Chroma ノードである。

現在の CLI は RPC を使わない。ピアとして Noise でノードに接続し、
`GetChainInfo` / `GetAccount` を投げている
（[`crates/chroma-cli/src/main.rs`](../crates/chroma-cli/src/main.rs) の `NodeClient`）。
RPC が要るのは、Rust と Noise 実装を持たない第三者のソフトウェア
—— ブロックエクスプローラ、取引所、他言語のウォレット —— を繋ぐときである。

## 2. トランスポート

| 項目     | 値                            |
| ------ | ---------------------------- |
| 規格     | JSON-RPC 2.0                 |
| 転送     | HTTP/1.1 `POST /`            |
| Content-Type | `application/json`     |
| 既定ポート  | 8332（P2P の 8333 と隣接させる）      |
| 既定の待受  | **無効**                       |

バッチ要求および通知（`id` なし）は JSON-RPC 2.0 の規定どおり扱う。

## 3. セキュリティ

RPC ポートはノードが乗り取られる古典的な入口である。
`0.0.0.0` に晒された JSON-RPC から資金が抜かれた事例は数え切れない。
そのため、次の3点を仕様として固定する。

* **既定で無効。** `--rpc-listen <addr:port>` を明示したときだけ待ち受ける
* **既定の待受はループバックのみ。** 外部に公開する場合はリバースプロキシと TLS を運用側の責任とする
* **ノードは秘密鍵を持たない。** 送金メソッドを設けない

3点目が最も重要である。`sendtoaddress` に相当するメソッドは存在せず、
署名は必ずクライアント側で行う。RPC は署名済みトランザクションを受け取るだけである。
これにより、RPC が漏れても盗めるものがない。

### 認証

`Authorization: Bearer <token>`。
トークンはノード起動時に `<data-dir>/rpc_token` へ生成し、パーミッション 0600 で書く
（node_key と同じ扱い）。トークンが一致しない要求は本文を読まずに `401` を返す。

## 4. 型の表現

| 種類            | 表現            | 例                    |
| ------------- | ------------- | -------------------- |
| ハッシュ          | 64桁 hex 小文字   | `"d1c3ba…"`          |
| アドレス          | bech32 文字列    | `"chr1ddmp…"`        |
| 金額・供給量・nonce  | **10進文字列**    | `"31000000"`         |
| 高さ            | 数値            | `486`                |
| bits          | hex 文字列       | `"0x1f400000"`       |
| 難易度           | 数値（浮動小数）      | `10.0`               |

金額を文字列にするのは、単位が 10⁻⁶ CHR であり、最大供給量が
100,000,000,000,000 units に達するためである。u64 の範囲は
JavaScript の `Number.MAX_SAFE_INTEGER`（2⁵³−1）を超えるので、
数値で返すと JSON をパースした時点で静かに壊れる。

難易度は `expected_hashes_log2` として浮動小数で返す。
整数に丸めると、2^12.00 から 2^10.27 への変化が「2^12 → 2^10」と表示され、
逆に 2^10.00 から 2^10.99 への変化が「変化なし」に見える。

## 5. メソッド

### 5.1 `chroma_getChainInfo`

引数なし。

```json
{
  "network": "chroma-mainnet",
  "height": 486,
  "tip": "5fd3a3d9f0a85546670c3b43fef7522eeb0774f913abe78aa2fbe3759ef146c2",
  "genesis": "…",
  "bits": "0x1f400000",
  "expected_hashes_log2": 10.0,
  "supply": "486000000",
  "pow": "randomx"
}
```

### 5.2 `chroma_getAccount`

`["chr1ddmplpspsertlny5n5vytfps7dc5w00edm00pd"]`

```json
{ "address": "chr1ddmp…", "exists": true, "balance": "31000000", "nonce": "0" }
```

存在しない口座はエラーではなく `"exists": false` と 0 を返す。
チェーンにとって「残高0の口座」と「知らない口座」は同じものである。

### 5.3 `chroma_getBlockByHeight` / `chroma_getBlockByHash`

`[486, 1]` / `["5fd3…", 1]`

第2引数は詳細度。省略時は `1`。

| 値   | 返すもの                    |
| --- | ----------------------- |
| `0` | 生ブロックの hex 文字列          |
| `1` | ヘッダ各フィールド + tx ハッシュの配列  |
| `2` | ヘッダ各フィールド + tx を展開したもの  |

```json
{
  "hash": "5fd3…",
  "height": 486,
  "version": 1,
  "previous_hash": "…",
  "state_root": "…",
  "tx_merkle_root": "…",
  "timestamp": 1757155200,
  "bits": "0x1f400000",
  "nonce": "8123441",
  "confirmations": 1,
  "transactions": ["…"]
}
```

`confirmations` は「アクティブチェーン上での先端からの距離 + 1」とする。
アクティブチェーン上にないブロック（負けた枝）については **`-1`** を返す。
Reorg で値の意味が変わるため、この扱いを仕様に含める。

### 5.4 `chroma_getHeader`

`[486]`

ヘッダのみを返す。軽量クライアントが PoW を検証するために使う。

### 5.5 `chroma_getMempool`

引数なし。

```json
{ "count": 3, "transactions": ["…", "…", "…"] }
```

### 5.6 `chroma_sendRawTransaction`

`["<署名済みトランザクションの hex>"]`

検証に通ればメンプールに入れ、ピアへ告知した上でハッシュを返す。

```json
{ "hash": "…" }
```

通らなければ `-32001` を返し、`data` に理由を入れる。

### 5.7 `chroma_getPeerInfo`

引数なし。

```json
[
  {
    "address": "60.151.51.203:8333",
    "node_id": "752b…",
    "direction": "outbound",
    "height": 486
  }
]
```

### 5.8 `chroma_getNodeInfo`

引数なし。

```json
{
  "version": "0.1.0",
  "node_id": "752b…",
  "noise_key": "c611…",
  "network": "chroma-mainnet",
  "peers": 1,
  "mining": true
}
```

## 6. エラー

JSON-RPC 2.0 標準の `-32600`〜`-32603` に加えて、次を定義する。

| code     | 意味                          |
| -------- | --------------------------- |
| `-32000` | ブロックまたはアカウントが見つからない         |
| `-32001` | トランザクション検証失敗（`data` に理由）    |
| `-32002` | 同期中のため答えられない                |
| `-32003` | この機能に必要な索引が構築されていない         |

## 7. 未定

### `chroma_getTransaction` を含めていない

トランザクションのハッシュから引くには、tx → ブロックの索引が要る。
`chroma-storage` は現在それを持たない。
入れる場合は storage に索引を追加し、既存のチェーンを再インデックスする作業が伴う。
ブロックエクスプローラを実装する段で必要になるので、そのときに決める。
索引なしのノードに問い合わせた場合は `-32003` を返す。

### 待受アドレスの既定値

`127.0.0.1:8332` を既定とするか、待受アドレスの指定を必須とするかは決めていない。
後者のほうが「気づかず公開してしまう」事故を防げる。

### 購読

ブロック着信を待つ購読（WebSocket など）は、この草案に含めない。
必要になった時点で、この仕様の上に別立てで設計する。
